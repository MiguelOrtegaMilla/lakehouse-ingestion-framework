# ADR-0005 — Batch write-ahead log and idempotent Delta writes

| | |
|---|---|
| **Status** | Accepted (2026-09-25) |
| **Related** | [ADR-0003](0003-control-plane-in-postgresql.md), [ADR-0004](0004-postgresql-coordinated-delta-logstore.md), [ADR-0006](0006-source-leases-with-epoch-fencing.md), [ADR-0010](0010-concurrent-write-conflict-handling.md) |

## Context

Writing data (Delta) and advancing state (PostgreSQL) touch two systems. There is no distributed transaction between them. A crash between the two must not duplicate data, lose data or leave the watermark inconsistent. Under Type 2 concurrency, other processes may commit to the same table at any time.

## Decision

### 1. Run ≠ Batch

| Concept | Identity | Meaning |
|---|---|---|
| **Run** | `run_id` = UUIDv7, generated by the instance (time-ordered, collision-safe without coordination) | One *attempt* |
| **Batch** | (`txnAppId`, `batch_seq`), allocated by the control plane | One *logical unit of data*: a watermark range or a file set |

A batch may take several runs (crash + recovery). **Idempotence is anchored to the batch, never to the run.**

### 2. `txnAppId` per (source, layer), not per table

| Run kind | `txnAppId` | `txnVersion` |
|---|---|---|
| Regular (full / incremental / new files / reprocess) | `<source_id>/<layer>` | `batch_seq`, monotonic per `txnAppId` |
| Backfill | `<source_id>/<layer>/backfill/<backfill_id>` | Chunk sequence within the backfill |

Why per (source, layer):
- With fan-in, one table is written by several sources; each needs its own idempotence track.
- A backfill has its own `txnAppId` so that it can run **concurrently** with the incremental run on the same table (Type 2) without either invalidating the other's sequence.
- Delta stores the latest `txnVersion` per `appId` in each table's log, so the same `appId` on different tables (Bronze, quarantine, Silver) is independent per table.

### 3. Protocol

1. Acquire the lease for the lease key (ADR-0006) → epoch E.
2. Look for a `PLANNED` batch for this `txnAppId`:
   - **found:** read the target table's `txn` version for `txnAppId`. If it is `≥ batch_seq`, the data was committed, so **roll forward** (step 7). Otherwise **replay** exactly the persisted plan (step 4).
   - **not found:** plan (connector `plan`) and persist the batch as `PLANNED`. This is the **write-ahead** step.
3. The plan is immutable once persisted. A `batch_seq` maps to exactly one plan, forever.
4. Read (connector `read(plan)`, replayable).
5. Write quarantine, then data, each with `txnAppId`/`txnVersion` and `userMetadata = {run_id, batch_seq, source_id}`, inside the commit context (ADR-0004 §3.7).
6. Delta's idempotent write skips any `txnVersion ≤` the recorded one: a replay after a crash is a no-op for data already committed.
7. In **one PostgreSQL transaction, conditional on `epoch = E`**: advance the watermark, mark the batch `COMMITTED` with its output Delta versions, and mark the run `SUCCEEDED`.
8. Release the lease.

### 4. Zombies (a writer that lost its lease but is still running)

- It cannot advance state: the step-7 transaction fails the epoch check.
- If it commits data for a stale batch, Delta ignores it (`txnVersion ≤` recorded).
- If it commits the *same* batch concurrently with the new holder, one of the two gets `ConcurrentTransactionException` (ADR-0010) and goes to the roll-forward check.
- It cannot write a *different* plan under the same `batch_seq`: plans are immutable (step 3).

### 5. Silver consumes Bronze by Delta version, not by `batch_seq`

With concurrent writers, `batch_seq` order is **not** commit order: seq 10 can commit after seq 11. A "max applied batch_seq" cursor would silently skip seq 10. The **Bronze Delta version** is the only total order of commits, so Silver's cursor is `last_applied_bronze_version`, and it reads new Bronze data by version range (Change Data Feed on the append-only Bronze table; cost verified in P10). Detail in ADR-0010.

### 6. Idempotent `MERGE`

Silver `MERGE` uses Delta's session-level `spark.databricks.delta.write.txnAppId` / `txnVersion` (internal confs, present in 4.4). They are **session-scoped**, so every concurrent task uses its own `SparkSession` (`spark.newSession()`); otherwise parallel tasks in one JVM would overwrite each other's settings. To be verified in P10.

## Alternatives

| Option | Verdict |
|---|---|
| Two-phase commit across Delta and PostgreSQL | Not supported by Delta; would need a coordinator. Rejected. |
| Keeping state inside the Delta table (derive the watermark from `max(updated_at)` in Bronze) | Breaks with backfills and late data; a full scan to plan; no audit. Rejected. |
| Deduplicate downstream instead of idempotent writes | Pushes correctness to every consumer. Rejected. |

## Consequences

- Exactly-once *effect* per batch under crashes, retries, zombies and concurrent writers.
- Mirrors Structured Streaming's offset log / commit log + idempotent `foreachBatch`, which keeps the door open to streaming.
- Depends on Delta internals to read `txn` versions (`Snapshot.transactions`). Isolated behind a small adapter and covered by an upgrade test.
